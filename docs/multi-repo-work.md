# Multi-repo milestones — work plan

Design: [ADR 0002](adr/0002-multi-repo-coordinator.md).

## Contract

One milestone can define, plan, build, and ship work across several Git repos,
both new (greenfield) and existing (brownfield). One task changes one repo.
Coordinator operations take one `--repo`; `members detect` inspects a checkout
without it. Joining a member adds no new tracked Path files there and leaves
an existing member `.project/` untouched.
Without `.project/MEMBERS.md`, behavior and output stay single-repo. See S5c
below for member task activation.

## Where Path assumes one repo

Function names, not line numbers, because main moves.

## Slices

Each slice ships in its own PR. Every slice changes all readers of any contract
it changes. A script that checks branch names accepts member names in the slice
that first runs it in a member: `git_guard` in S2b; `isolation`, `dispatch_driver`,
and `build_state` in S3c1-S3c3; `integration`, `archive_milestone`, `pipeline_undo`,
`pipeline_diagnose`, and `pipeline_git` retirement in S4. `STATE.branch` stays the
coordinator's `feature/milestone-001`, so `pipeline_state` keeps its branch parser;
its build-entry transition locks member branches in S3b. Until then those
scripts refuse member names, which fails safe. S1–S4 leave the no-`MEMBERS.md`
path and output unchanged.

| S2a Member role | `members add` writes an untracked marker in the member's shared Git directory (`$(git rev-parse --git-common-dir)/gsd-path/member.json`) naming the absolute coordinator path, project, and member name. `members.member_role` verifies it from any worktree of the member: the coordinator exists, its project matches, and its `MEMBERS.md` lists this name at this Git common dir. Joining and pre-push require that resolvable baseline; a missing ref fails closed with a `git fetch origin` hint. Deleting a reserved ref needs `members.authorize_delete` for that ref at its expected remote SHA. A stale marker blocks commit and push with the repair hint. |

| S3c2a Member landing write path | `isolation.land_member` commits and proves the member source commit in the member sidecar (parent `member_base`, only the contract's `files`, subject from the contract, body `Task`/`Base: member_base`/`Contract: base`/`Files`), writes a journal in the coordinator Git directory, cherry-picks into the member bound checkout only while its tip equals the journaled parent, proves the landing against that parent, then makes a `.project`-only coordinator record commit (`Task`, `Base`, `Member: <name> <landing> <member_base>`) that stamps the task `done` with `base` and `member_base`. The copy path must be untracked, with real directories and a regular non-symlink file inside the sidecar. | S4b1a Member direct integration | `integration.integrate_member(coordinator, member, archive_path, reviewed_head)` closes one member in `direct` mode. It requires the local member bound branch `feature/<coord>-milestone-001` at the reviewed HEAD and a `main` remote default. It creates the two-parent merge `integrate: <coord> M00N — merge feature/<coord>-milestone-001 into main` with body `Archive:`, `Member:`, and `Reviewed-HEAD:` lines in a `chore/integrate-<coord>-m001` sidecar on `origin/main`; its second parent must be the reviewed HEAD. An unpublished canonical merge is reused when its first parent is still `origin/main`, else rebuilt. An integration branch left at its creation base is discarded and recreated. If the reviewed HEAD already reached `origin/main` without a canonical member merge, integration stops for user-approved recovery. It publishes in order: the bound branch (absent only; a different remote SHA blocks), `main` (only when the merge is not on `origin/main`), then the annotated tag `milestone/<coord>-<archive-name>`. Before each push it authorizes that exact ref and object for the member pre-push hook. A rerun finds the published merge in `origin/main` first-parent history and publishes only missing refs, so a member is never integrated twice. `validate_member_integrated` refreshes `origin` by default and checks the canonical merge on `origin/main` with the reviewed HEAD as second parent and the published annotated tag at that merge. | S4b1b Member pull-request integration | `integration.integrate_member_pull_request(coordinator, member, archive_path, reviewed_head)` closes one member in `pull-request` mode. It requires the same local bound tip and `main` default as direct mode, publishes the bound branch under its push authorization, and opens or reuses one GitHub or Azure Repos PR from `feature/<coord>-milestone-001` to `main`. A new PR uses the member merge subject as its title and the member integration metadata as its body, without attribution. Reuse keeps the existing title and removes legacy tool attribution while preserving human content. While the PR is open it returns `awaiting-merge`; a PR closed without merging blocks. After a user-completed provider merge, it requires merge provenance (no auto-merge; Azure also refuses policy bypass and requires no-fast-forward), a two-parent merge on `origin/main` first-parent history whose second parent is the reviewed HEAD, and removes legacy tool attribution while preserving human content before publishing the annotated tag `milestone/<coord>-<archive-name>` under its tag authorization. | S4b2b Post-commit checks and ship instructions | `archive_milestone.validate` parses the ship body's member lines (`pipeline_git.ship_member_rows`) and requires them to name exactly the archived lock's members in lock order at their `FINAL.md` member reviewed heads, then requires the exact body with those lines; it returns them as `members`. `validate-integrated` checks each named member with `validate_member_integrated` and requires its merge and tag to equal the ship body's. `isolation.publication_base` (rebase-adoption publication) is unchanged, so it fails closed for a member milestone. | S4c4 Member rebase adoption | A member bound branch never receives a merge of its default branch. When the member's recorded default branch moved, an explicit owner ruling runs `isolation.py adopt-member-rebase --repo <coord> --member <name> --onto <fetched origin/<recorded> SHA> --ruling <verbatim>` (`--dry-run` is read-only and simulates the replay in a disposable object store; `--abort` rolls back only a `prepared` or `replayed` apply). Legal coordinator states are `plan/active`, `plan/blocked`, `build/blocked`, and ship while STATE.archive is null, with no in-progress task, member task branch or authorization, pending helper journal, dirty Path bound checkout, or integrated member-close row. `--onto` must equal the live and freshly fetched `origin/<recorded>`, descend from the locked base, and not contain the bound tip; the remote bound branch must be absent or at the local tip. The helper journals in `<coord common dir>/gsd-path/member-rebase/<member>.json`, cherry-picks the linear locked range on `chore/rebase-<coord>-milestone-NNN-<member>`, and proves one replay per original commit with the same message, author, and ordered edits; landing task contracts must still hold. A conflict, empty commit, or failed proof rolls back. It keeps the old tip at `refs/gsd-path/member-rebase/<coord>/<member>/<old tip>`, journals `publishing`, and pushes under an exact lease. After that it only rolls forward, unless the remote's per-ref report rejected a push that began at `replayed` and the ref keeps its lease (`publish-refused`, back to `replayed`). It then compare-and-swaps the local bound branch, refreshes Path's bound checkout, preserves a pending close row while proving the same PR remains open/unmerged before and after publication, and commits the new lock base with `.project/build/member-rebase-adoption.json` (`gsd-path/member-rebase-adoption/v1`) in one `.project/`-only coordinator commit. `_recover_task` maps a recorded landing and member base through the receipt chain and reports `provenance: owner-ruled-member-rebase`; `verify-landed`, ship inputs, `close-members`, the coordinator-migration baseline, and legacy projections read the same chain and refuse a receipt whose map no longer recomputes or whose base differs from the lock. Status lists a pending journal as `member_rebase`; undo refuses it and the adoption commit; diagnose names the rerun or `--abort`. Member isolation and landing wait while that member's journal is pending. Verify evidence and final reviews at old member commits do not carry over. `define/active` refuses without touching a pending close; normal gates first reach a quiet legal entry. The receipt's `prior_close` preserves the old row and open-PR source proof. After fresh FINAL/publication, `close-members` may rebind that pending close and lease-advance only canonical repair landings to the same PR; it never creates a replacement PR for a lost, completed, or abandoned one. |
| S4d Member lookahead drift | Replaces the S3d fail-closed rule. At lookahead plan approval, `state_checkpoint` records each member named by a not-done lookahead task at the base its brief was checked at (the member's `origin/main`, or the locked bound tip during a member build) in `<coord common dir>/gsd-path/lookahead-member-bases/<milestone>.json`. At promotion, `_classify_plan_drift` diffs each member from that base to the member merge the shipped milestone's ship commit names; a declared member path in that diff flags the task as `<member>:<path>` drift. A member the shipped milestone did not close has no Path change, and later team pushes are caught by build brief lint. Both commits are fixed, so re-validating a completed promotion gives the same result. Missing recorded bases stay `unverifiable`, which reopens Plan. |

## Decisions

1. Member remote default must be `main`; `members add` refuses others.
   Replaced on 2026-10-10 (issue #372): `members add` records the member
   default branch in `.project/MEMBERS.md`, and each member path reads it.
2. Each member may set `direct` or `pull-request` in `.project/MEMBERS.md`.
   The milestone mode is the default.
3. The coordinator may be a product repo or a dedicated program repo.
